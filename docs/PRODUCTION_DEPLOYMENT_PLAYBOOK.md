# YUVA Club Version 2.0 Production Deployment Playbook

This playbook governs an approved YUVA Club production release. It does not authorize a deployment. The production GitHub environment must require Founder approval.

## Release inputs

- Full 40-character commit SHA already reviewed and present on `main`
- Tracked-files-only ZIP and SHA-256 generated by the production workflow
- Fresh verified backup under `/home/data/yuva-release-1.0.1-YYYYMMDDTHHMMSSZ`
- Current-production rollback artifact and mutable-data manifests
- Approved maintenance window and named release operator

## Pre-deployment checklist

- [ ] Founder has issued explicit production approval.
- [ ] Release commit is the expected commit on `main`.
- [ ] No other deployment is running.
- [ ] GitHub `production` environment approval is enabled.
- [ ] Production App Settings have been recorded with secret values protected.
- [ ] `SQL_APPROVAL_ENABLED` remains false unless separately approved.
- [ ] No production database or schema change is included.
- [ ] Artifact contains exactly the tracked files from the expected commit.
- [ ] Artifact contains no `.git`, `.env`, credentials, previews, review artifacts, or mutable runtime directories.
- [ ] Staging acceptance and all release regressions passed for the same commit.
- [ ] Public rollback and incident contacts are available.

## Backup verification

The backup must contain:

- `archives/current-production-application.tar.gz`
- `archives/submissions.tar.gz`
- `archives/portal-data.tar.gz`
- `archives/portal-uploads.tar.gz`
- relative file lists and SHA-256 manifests under `manifests/`
- `verification-report.txt` ending with `OVERALL_VERIFY=PASS`

Create the backup from two identical snapshots rather than archiving the live
Azure Files application tree directly:

```bash
bash tools/create-consistent-production-backup.sh \
  /home/site/wwwroot \
  /home/data/yuva-release-1.0.1-YYYYMMDDTHHMMSSZ
```

The tool keeps mutable paths in separately verified archives, fails if the
source does not stabilize, and verifies every archive by extracting it and
comparing its manifest with the frozen snapshot.
- redacted production configuration metadata

Verify the report without printing mutable filenames:

```bash
ROOT=/home/data/yuva-rc1-release-gate-YYYYMMDDTHHMMSSZ
test -f "$ROOT/verification-report.txt"
grep -qx 'OVERALL_VERIFY=PASS' "$ROOT/verification-report.txt"
sha256sum "$ROOT/archives/"*.tar.gz
```

Stop if any expected archive, manifest, checksum, or verification result is missing.

## Deployment

1. Open the `Production release - YUVA Club` workflow.
2. Use `validate` first to exercise GitHub parsing, exact-commit checkout,
   regression tests, tracked-file packaging, safety-control inspection, and
   rollback-artifact retention without contacting Azure or entering the
   protected production environment.
3. After that run passes and Founder approval is recorded, start a separate
   dispatch and select `deploy`.
4. Enter the exact reviewed commit SHA.
5. Enter the fresh verified backup root.
6. Enter `DEPLOY_YUVACLUB_PRODUCTION`.
7. Review the validation job's commit, file inventory, test results, artifact size, and SHA-256.
8. Approve the protected `production` environment.
9. The workflow deploys with `az webapp deploy --type zip --clean false`.
10. The workflow stops on a backup, deployment, mutable checksum, or smoke-test failure.

Do not run a second manual deployment while this workflow is active.

## Smoke tests

The automated public smoke test requires successful responses from:

- `/`
- `/registration.php`
- `/portal-login.php`
- `/parent-login.php`
- `/admin-login.php`
- `/privacy.html`
- `/terms.html`
- `/contact.html`

Manually verify:

- correct Version 2.0 branding and navigation
- responsive public and login pages
- generic authentication failures
- no exposed configuration or diagnostic details
- no broken links or missing assets
- no unexpected HTTP 5xx responses

Use staging for comprehensive Student, Parent, and Master Admin acceptance. Use production identities only when the Founder separately authorizes specific existing accounts.

## Post-deployment verification

- [ ] Deployment ID and result recorded.
- [ ] Deployed commit and artifact SHA-256 recorded.
- [ ] Production App Settings unchanged.
- [ ] `submissions`, `portal-data`, and `portal-uploads` checksums match the pre-deployment manifests.
- [ ] Mutable file counts have not decreased.
- [ ] Public smoke tests pass.
- [ ] Application logs contain no repeated 5xx responses.
- [ ] Homepage and legal/contact pages show the approved release.
- [ ] No concurrent or automatic follow-up deployment occurred.

## Rollback

Trigger rollback immediately if:

- mutable verification fails
- the wrong commit or artifact is deployed
- authentication or authorization regresses
- public pages produce repeated 5xx responses
- a release-blocking workflow is broken

Prepare the exact current-production application package:

```bash
ROOT=/home/data/yuva-rc1-release-gate-YYYYMMDDTHHMMSSZ
mkdir -p "$ROOT/rollback-release"
tar -xzf "$ROOT/archives/current-production-application.tar.gz" \
  -C "$ROOT/rollback-release"
(cd "$ROOT/rollback-release" && zip -qr "$ROOT/current-production-rollback.zip" .)
sha256sum "$ROOT/current-production-rollback.zip"
```

Deploy that rollback ZIP through a separately approved controlled OneDeploy operation with cleaning disabled. Then restore mutable archives only if the deployed directories are absent or their pre-deployment files are missing:

```bash
ROOT=/home/data/yuva-rc1-release-gate-YYYYMMDDTHHMMSSZ
WWW=/home/site/wwwroot

tar -xzf "$ROOT/archives/submissions.tar.gz" -C "$WWW"
tar -xzf "$ROOT/archives/portal-data.tar.gz" -C "$WWW"
tar -xzf "$ROOT/archives/portal-uploads.tar.gz" -C "$WWW"

(cd "$WWW" && sha256sum -c "$ROOT/manifests/submissions.sha256")
(cd "$WWW" && sha256sum -c "$ROOT/manifests/portal-data.sha256")
(cd "$WWW" && sha256sum -c "$ROOT/manifests/portal-uploads.sha256")
```

Never overwrite a changed mutable directory automatically. If post-backup writes occurred, stop and reconcile them before restoration.

## Release record

Record:

- approval time and approver
- deployed commit
- artifact filename, size, and SHA-256
- backup root and archive checksums
- Azure deployment ID and result
- mutable verification result
- smoke-test result
- rollback decision and final production status
